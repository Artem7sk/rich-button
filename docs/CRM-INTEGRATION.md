# PaidFlow + CRM: граница интеграции

Статус: проект объединения, не реализованная синхронизация.

10 октября 2026 пользователь предложил CRM по адресу https://prodasha.duckdns.org/crm/ как основу общего продукта. В браузерной проверке адрес вернул 502 / Connection refused. Исходники и API CRM пока не доступны. Перечень её функций получен от пользователя и ещё не проверен.

## Целевой продукт

CRM хранит организации, контакты, сотрудников, задачи, документы, счета, оплаты и историю. Android-приложение даёт доступ к этой же базе, распознавание документов, быстрые действия и локальные черновики. Автопарк и заезды — отдельный включаемый модуль для сервисов; основной учёт клиентов и оплат остаётся применимым другим компаниям.

## Данные и ответственность

| PaidFlow | CRM | Правило переноса |
| --- | --- | --- |
| Клиент: имя, БИН/ИИН, адрес и банк | Организация + реквизиты | Сначала сопоставление по БИН/ИИН; совпадение только имени требует проверки |
| Email и телефон | Контакт организации | Не заменять существующие контакты без выбора пользователя |
| Счёт: строки, валюта, срок, снимок сторон | Счёт организации | Сохранять валюту и точные денежные единицы; исходный номер хранить отдельно, если номера конфликтуют |
| Частичные оплаты | Платежи по счёту | Уникальный ключ каждой операции, защита от повторной загрузки |
| Журнал напоминаний | История действий | Не считать запись напоминания доказательством отправки сообщения |
| OCR | Черновик организации или счёта | Сначала просмотр и исправление; только потом сохранение на сервер |

## Требования к подключению

1. Прочитать исходники, миграции и существующий контракт API; не придумывать маршруты для работающего сервера.
2. Согласовать источник истины: после подключения сервер отвечает за сохранённые счета и платежи, телефон — за незавершённые черновики.
3. Авторизация каждого сотрудника и серверная проверка ролей. Для продажи нескольким компаниям — изоляция данных компаний во всех запросах, файлах и поиске.
4. HTTPS, отзываемые сессии, защищённое хранение токена на Android. Никаких встроенных общих логинов и паролей.
5. Удалённые страницы не получают доступ к JavaScript-мосту Native, который читает и записывает локальную базу. UI остаётся локальным, запросы идут через отдельный клиент API.
6. Импорт локальной базы: резервная копия, предварительный список совпадений и конфликтов, подтверждение, транзакция, отчёт. Повтор импорта не создаёт дубли.
7. Очередь изменений с идентификаторами операций и версиями записей. При конфликте редактирования — явный выбор пользователя; оплаты не перезаписываются по правилу «последний победил».
8. Сначала подключить организации, счета и оплаты; затем задачи, историю, документы, автопарк и уведомления.

## Проверки при приёмке

- Менеджер видит только разрешённые организации; сотрудник другой компании не получает их через API и файлы.
- Фото реквизитов на телефоне создаёт проверяемый черновик; подтверждённая организация появляется в CRM.
- Счёт и частичная оплата отображаются одинаково на телефоне и компьютере.
- Повтор запроса и восстановление связи не дублируют организации, счета и платежи.
- Локальные данные предыдущего APK не теряются при переходе.

## Что необходимо получить

Репозиторий CRM либо архив исходного проекта без .env, паролей, ключей и базы клиентов. Если сервером управляет отдельный агент, он может выгрузить исходники и описание API в предоставленный пользователем репозиторий. Публичный адрес интерфейса и административный вход не заменяют доступ к коду.

## Онлайн и офлайн — обязательное требование пользователя

Оба режима входят в один продукт. Текущая версия PaidFlow уже работает локально; объединение с CRM не должно превращать её в страницу, требующую постоянного интернета.

Офлайн доступны: локально загруженные организации и контакты, создание и редактирование черновиков счетов, распознавание фото на устройстве, запись частичных оплат, задачи и заметки, PDF и резервная копия. Фото и вложения остаются в очереди до отправки. Данные других сотрудников и серверные уведомления обновляются при связи. Оплата в этом контексте — запись об оплате, не банковский перевод.

Для реализации требуется локальная база и журнал исходящих операций. Изменение данных и постановка операции в очередь должны сохраняться атомарно. Каждая операция имеет уникальный ID, ID компании, ID устройства, версию исходной записи и серверный результат. Повтор после сетевого сбоя безопасен благодаря серверной идемпотентности. Платежи добавляются и отменяются отдельными событиями; повторная отправка не увеличивает сумму оплаты.

Интерфейс показывает: «Офлайн», «Ожидает отправки», «Синхронизировано», «Нужно разрешить конфликт», дату последней синхронизации и число ожидающих операций. Нельзя показывать «Синхронизировано», пока сервер не подтвердил запись. Конфликт счёта не разрешается тихим перезаписыванием. Общие номера счетов назначает сервер; до синхронизации используется отдельный временный номер с префиксом устройства, чтобы два менеджера не выдали один номер.

После первого входа устройство сохраняет разрешённый набор данных компании. Для нового устройства первоначальная авторизация требует сети. Политика доступа после истечения сессии и отзыва сотрудника должна быть определена до реализации: офлайн-режим не даёт возможность мгновенного удалённого отзыва уже скачанных данных. Локальный экспорт и выход не должны незаметно уничтожать неотправленные изменения.

Проверки: режим полёта, закрытие приложения и перезапуск телефона с очередью, повторная доставка платежа, обрыв соединения после принятия операции сервером, конфликт двух менеджеров, импорт старой базы, истечение сессии во время синхронизации.

Там же сообщалось о потере БД `orgcrm` при сохранённых исходниках. Эти сведения ещё не проверены по текущим файлам. Не смешивать ORG CRM с отдельной действующей CRM автосервиса на SEMEY. Для следующего шага нужен архив этой рабочей копии либо её репозиторий, без секретов и пользовательской базы.
